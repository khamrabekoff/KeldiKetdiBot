# Эксплуатация и обслуживание

Практическая справка: как выкатить изменения, что делать при поломке,
как восстановить данные.

---

## Как выкатывается обновление

```bash
git push origin main
curl -s "https://xamrobekov.pythonanywhere.com/deploy/<DEPLOY_SECRET>"
```

Второй вызов делает на сервере `git pull` и перезапускает приложение.
**Заходить в консоль PythonAnywhere для обычных правок не нужно.**

Секреты — в `.env` на сервере, в репозиторий не попадают.

---

## Служебные адреса

Все закрыты секретом из `.env`.

| Адрес | Назначение |
|---|---|
| `/health` | Жив ли сервис (без секрета) |
| `/status/<DEPLOY_SECRET>` | Версия, время, счётчики, готовность клиента Telegram |
| `/logs/<DEPLOY_SECRET>?n=60` | Последние строки лога ошибок |
| `/deploy/<DEPLOY_SECRET>` | `git pull` + перезапуск |
| `/cron/reminders/<CRON_SECRET>` | Напоминания |
| `/admin/broadcast/<DEPLOY_SECRET>` | Рассылка (POST, JSON) |

### Как читать `/status`

```json
{"runtime": {"inits": 1, "updates": 47, "errors": 0, "last_ms": 465}}
```

- `inits: 1` при растущем `updates` — **норма**, соединение переиспользуется
- `inits` растёт вместе с `updates` — соединение рвётся, смотреть логи
- `errors > 0` — были сетевые сбои

## Проверка напоминаний без спама

```bash
curl -s ".../cron/reminders/<CRON_SECRET>?kind=evening&dry=1"
```

`dry=1` показывает **кому бы ушло**, ничего не отправляя.
**Всегда проверяйте так перед настоящей отправкой** — сообщения идут живым людям.

## Ограничения бесплатного тарифа

Их важно помнить, иначе легко предложить нерабочее решение.

**1. Фоновые потоки не работают.** `threading.Thread` формально живёт,
но не получает процессорное время. Проверено диагностикой.
Поэтому event loop крутится в потоке запроса, а не в фоновом.

**2. Консоль и Tasks не могут достучаться до `api.telegram.org`** —
внешний прокси возвращает 503. Само веб-приложение может.
Поэтому напоминания запускаются не скриптом, а обращением к собственному адресу.

**3. Задачи в расписании может не быть вовсе.** Аккаунту `xamrobekov`
бесплатная ежедневная задача досталась и занята утренним напоминанием.
Новым аккаунтам PythonAnywhere её больше не даёт — проверено на `xamrobekov`
4 сентября 2026: вкладка Tasks предлагает только платный тариф.

Поэтому **оба** напоминания умеют срабатывать на обычном трафике бота:
утреннее — в окне от получаса до начала рабочего дня и два часа после,
вечернее — после его конца. Флаг в таблице `settings` не даёт отправить
дважды, так что задача и трафик друг другу не мешают: кто первый, того и
отправка.

Цена такого способа — напоминание уходит не по будильнику, а когда боту
напишет первый человек. Если утром боту не написал никто, утреннее
напоминание в этот день не уйдёт. Кому нужна гарантия по часам — платный
тариф или внешний планировщик, дёргающий `/cron/reminders/<CRON_SECRET>`.

Недельная сводка и резервная копия прицеплены к утреннему запуску.

**4. Задача и сайт периодически истекают.** Нужно заходить и жать
**Extend expiry** во вкладке Tasks (если задача есть) и
**Run until 1 month from today** во вкладке Web.
Иначе бот и напоминания просто перестанут работать.

## Восстановление из резервной копии

Копии приходят админам в Telegram файлом `keldi_ketdi_YYYYMMDD_HHMM.db`.

1. Скачать файл из Telegram на компьютер
2. PythonAnywhere → **Files** → перейти в `/home/xamrobekov/`
3. Переименовать текущий `keldi_ketdi.db` (например в `keldi_ketdi_broken.db`) —
   **не удалять**, пока не убедитесь, что восстановление удалось
4. Загрузить скачанный файл и переименовать в `keldi_ketdi.db`
5. Открыть `/deploy/<DEPLOY_SECRET>` чтобы перезапустить
6. Проверить `/status/...` — количество пользователей должно совпасть

## Если бот не отвечает

По порядку:

1. `/health` — приложение вообще живо?
2. `/logs/<DEPLOY_SECRET>?n=60` — что в логе
3. `/status/<DEPLOY_SECRET>` — готов ли клиент Telegram
4. Не истёк ли срок сайта во вкладке **Web** (см. ограничения выше)

**Частые причины из практики:**

| Симптом в логе | Причина |
|---|---|
| `httpx.ProxyError: 503` | Временный сбой прокси. Обрабатывается автоматически: 3 попытки. |
| `ExtBot is not properly initialized` | Прокси оборвал инициализацию на полпути. Пересоздаётся само на следующем сообщении. |

**Про `ExtBot is not properly initialized` — важное.** До 4 сентября 2026
самовосстановление было заявлено, но не работало: PTB ловит это исключение
внутри `process_update` и только пишет в лог, наружу оно не выходит, флаг
готовности оставался поднятым, и воркер молча ронял все сообщения — при этом
`/status` показывал `errors: 0`. Симптом: бот не отвечает, `updates` растёт,
ошибок ноль, а в логе повторяются трейсбеки.

Починено с двух сторон: зарегистрирован обработчик ошибок, который замечает
этот случай и помечает клиент на пересборку, а сама инициализация теперь
проверяет, что ExtBot действительно поднялся, и не засчитывает полусобранный
запуск за успех.

Если симптом вернётся — сначала смотреть `errors` в `/status`: теперь он
считает и то, что PTB глотает.
| `IndentationError` после правки через веб GitHub | Правка через браузер сломала отступы. **Загружайте файл целиком, не редактируйте в браузере.** |

## Локальный запуск

```bash
pip install -r requirements.txt
cp .env.example .env    # заполнить своими значениями
python run_local.py      # режим polling, только для разработки
```

Проверка синтаксиса перед выкаткой:

```bash
python -m py_compile app.py ui.py database.py settings.py analytics.py
```
